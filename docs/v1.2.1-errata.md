## E-001 — Review.status schema default contradicts prose

**Location:** §7.10 Review data model, `status` column; §3.8.2 "Creation" paragraph.

**Problem:** §3.8.2 states "A new review starts open by default," but the §7.10 column definition reads `DEFAULT 'draft'`. Implementation following the schema would silently create reviews in draft, breaking the expected reviewer-notification flow.

**Fix:** Changed the column default from `DEFAULT 'draft'` to `DEFAULT 'open'`. No change to the prose.

---

## E-002 — Derived review statuses stored as bare enum without denormalization note

**Location:** §3.8.2 "State ownership" paragraph; §7.10 index note.

**Problem:** The spec describes `open`, `changes_requested`, and `accepted` as derived from participant decisions, but the `Review.status` column is modeled as a plain stored enum with no indication that it is a denormalized cache. A reader could reasonably implement it as either the source of truth or a cache, and the two strategies have different write semantics and failure modes.

**Fix:** Added clarification to both locations: "The Review.status column stores the current derived value as a denormalized cache; the service layer recomputes it on every participant-decision write and on new-revision reset."

---

## E-003 — `decision=comment` has no defined status-transition semantics

**Location:** FR-REVIEW-09.

**Problem:** The publish-drafts endpoint accepts `decision` values `comment`, `changes_requested`, `accepted`, `resolved`, and `closed`. The latter four correspond to review statuses or explicit state transitions, but `comment` is not a review status and has no defined transition rule. Without a clarification, an implementer might treat `comment` as an error or invent a transition.

**Fix:** Appended to FR-REVIEW-09: "comment is not a review status; it publishes the batch without triggering a status transition."
